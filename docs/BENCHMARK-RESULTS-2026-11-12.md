# EasyMall MySQL 并发性能基线与瓶颈分析

日期：2026-11-12（Asia/Shanghai）。本次实际运行结果；没有部署 Redis、MQ 或修改业务逻辑。

## 结论

当前已确认两个瓶颈：关键词分页反复扫描并精确统计总数；热点商品/同用户写入的行锁竞争。连接池等待是这些慢操作及事务持有连接较久的外在表现。公开商品详情没有锁等待或明显连接池等待，不能根据吞吐平台就把其瓶颈归因到数据库，也不能承诺缓存会带来固定倍数提升。

先处理昂贵查询，再按业务键控制热点写入并发。Redis 的首个落点应是可复用的搜索结果总数/热门结果缓存和入口限流；不要直接把库存正确性迁到 Redis。现有同步下单没有外部通知等耗时步骤，暂不将 MQ 作为提高下单吞吐量的首选。

## 环境与方法

- Windows 11；Intel Core i7-14650HX，24 逻辑 CPU，约 16 GB 内存；应用、MySQL、驱动同机，其他桌面应用仍在运行。
- MySQL 8.0.34 独立进程，127.0.0.1:13327；应用 127.0.0.1:18081。未使用或修改已有 MySQL 数据库。
- Java 21.0.7，应用堆 128～384 MB；InnoDB buffer pool 256 MB；Hikari 最大连接数 20；只在隔离应用启用 Actuator metrics，保持 WARN 日志级别。
- MySQL innodb_flush_log_at_trx_commit=1，sync_binlog=1，log_bin=1；未降低持久性要求。
- 64 个独立买家及地址、65 个有库存商品、10000 个查询专用商品，另有 20 个应用初始化商品。每次下单 1 件、价格 12.30、clearCart=false，唯一幂等键，不混入登录耗时。
- 24 组梯度：1/8/32/64 并发，每组预热 3 秒、正式测量 15 秒；另做 6 组 64 并发、预热 5 秒、测量 30 秒的换序复测，以及 1 组 20 秒搜索 CPU 诊断。
- 闭环、HTTP keep-alive、无自动重试；统计响应接收及 JSON 校验完成时的延迟。监控流量不计入业务请求，但其数据库操作会进入低比例的 SQL 统计。
- 初始化和暖场请求排除出吞吐与延迟；库存一致性核验同时覆盖暖场与正式下单。

## 瓶颈证据与建议

### 1. 关键词分页：COUNT 扫描与数据库 CPU

30 秒复测中，COUNT 执行 7923 次，累计 593522.1 ms，检查 79744995 行，平均每次 10065 行。当前页查询累计仅 3674.9 ms。COUNT 累计时间可超过 30 秒，因为多个数据库线程同时执行。

额外 20 秒诊断：255.1 请求/秒，p95 312.2 ms。正式采样窗口内 MySQL 平均约 18.9 个逻辑 CPU 的计算量（按整机 24 逻辑 CPU 归一化为 78.6%），系统 CPU 平均 95.6%。这与 SQL 扫描证据一致。

代码位置：CatalogService.products 使用 LIKE %keyword%；Db.page 每次先 COUNT，再查询当前页。已有分类索引并不能避免对关键词匹配逐行判断。执行计划详见 diagnostics JSON。

优先方案：评估是否需要每页精确 total；可以在协议允许时采用 hasMore 或降低总数更新频率。若必须保留 total，针对热门、可复用条件增加短 TTL 的 Redis 计数缓存，必要时缓存热门结果 ID。缓存键覆盖分类、关键词、上下架条件；事务提交后失效，处理回填竞争、过期抖动与受控回源。不要无界缓存所有任意搜索词，也不要认为加普通 name 索引即可解决前置通配符搜索。

### 2. 热门商品：数据库行锁竞争

复测中最耗时 SQL 为 SELECT * FROM product WHERE id=? FOR UPDATE；采样等待关系位于 product 表。不同商品的分散下单没有行锁等待。这证明热点写入存在真实串行化，但并不证明其是整机唯一瓶颈。

先减少事务内串行往返和持锁期间的非必要查询，保留数据库条件扣库存和唯一约束；评估按商品/用户限流与有界并发。Redis 可承担多实例一致的入口限流，但限流属于过载保护，不等于成功订单吞吐变高。不要仅将数据库行锁替换为 Redis 分布式锁。

### 3. 同用户：用户行锁串行化

复测最耗时 SQL 为 SELECT id FROM mall_user WHERE id=? FOR UPDATE，锁等待集中在 mall_user。该锁是现有幂等、购物车与订单并发控制的一部分，不能为了性能直接删除。普通容量测试应使用多个真实独立账号；对同账号重复点击可先限流。后续若缩小锁范围，必须重新验证同键下单、支付/取消竞争及购物车一致性。

### 4. 鉴权与普通详情

带 token 的商品请求多一次 auth_token 与 mall_user 关联查询，公开详情没有这笔查询。两轮结果均显示其有额外成本，可作为后续会话存储优化候选；但鉴权缓存必须保留注销、过期和权限变更的失效语义。普通详情的 SQL 本身很快，且未观察到连接池耗尽；其吞吐平台还包含 HTTP/JDBC 往返、应用执行和同机调度开销，不以本次数据承诺 Redis 提升倍数。

### 5. 为什么暂不直接引入 MQ 或预扣库存

MQ 能缓冲短期洪峰，不能提高同一数据库热点行的固有处理速度。将当前同步下单改为异步受理会改变 API 语义，还需结果查询、Outbox、消费幂等、重试、死信和失败补偿。Redis 预扣库存还增加 Redis/MySQL/消息之间的一致性问题。当前证据支持先优化搜索读与热点入口控制；若未来增加通知、统计、独立秒杀场景，再引入 MQ，并测最终订单完成延迟而不只测入队速度。

## 正确性与失败情况

- 31 组正式测量，共 204850 个业务请求，另有 39665 个预热请求；失败 0，监控错误 0。初始化、冒烟验证及监控流量不在这些请求数中。
- H2 集成测试 14/14 通过；独立 MySQL 测试库同样 14/14 通过。新增不同买家/商品并行一致性与多商品反序请求测试，未设置机器相关性能断言。
- 最终数据库中有 53723 个订单（含冒烟与暖场），负库存 0，库存余额与流水不一致 0，订单金额与明细不一致 0。
- 每组购买测试核对订单数和金额，并确认每笔订单只有一条对应商品的扣库存流水。

## 限制与下一步

这是开发机上的短时闭环基线，不能当作生产 QPS 承诺、固定到达率洪峰测试或长期稳定性结论。客户端 CPU 未达到单核满载，但同机调度和后台活动仍有影响；数据库和 JVM 缓存、订单数据量也随运行变化。正式上线容量需使用独立压测机、持续稳态与固定到达率测试。

建议下一轮只改一个变量：先实现搜索总数/热门结果的 Redis 缓存，再用相同数据与查询分布对比冷缓存、热缓存、低命中率、失效和 Redis 故障；随后独立验证入口限流。保持当前事务/库存正确性测试作为回归门槛。
